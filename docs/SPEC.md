# PM Agent — Project Spec

## 1. What this is

An AI agent for portfolio managers. A PM asks questions in plain English ("where are we most
overweight vs the benchmark?", "if I sell $2M of NVDA, do we still breach anything?") and the
agent answers using tools on our own MCP server. Every morning before market open, the agent
also runs on its own and writes a short **morning brief** of what changed overnight and what
needs attention.

The project demonstrates four things: **agents, MCP, automation, and
metrics**. The finance is deliberately simple arithmetic so the effort goes into the agent
engineering and into proving it works.

**The one rule everything follows: the agent never does math.** Tools compute every number
in code. The agent decides which tools to call, in what order, and explains the results.

## 2. Users

- **Primary:** a portfolio manager running a fund against a benchmark (e.g. the S&P 500),
  with risk limits set by their firm.
- **Variant (later):** an ETF issuer running leveraged single-stock funds, where the check is
  "did each fund deliver its target (e.g. 2x the stock's daily return)?" instead of
  "how do we compare to the benchmark?" See task M8.

## 3. Architecture

```
  PM question / daily schedule
              │
              ▼
   ┌──────────────────────┐        ┌──────────────────────┐
   │  Agent (harness)      │◄──────►│  Claude API           │
   │  agent loop, prompts, │        │  (model picks tools,  │
   │  logging, limits      │        │   writes answers)     │
   └──────────┬───────────┘        └──────────────────────┘
              │ MCP (stdio)
              ▼
   ┌──────────────────────┐
   │  MCP server           │  thin layer: load data, call analytics, format output
   └──────────┬───────────┘
              ▼
   ┌──────────────────────┐        ┌──────────────────────┐
   │  analytics.py         │◄───────│  data.py              │
   │  pure functions,      │        │  portfolios, prices,  │
   │  all the math         │        │  benchmarks, sectors  │
   └──────────────────────┘        └──────────────────────┘

   Eval harness: runs the agent on test questions and planted events, scores it, saves results.
   GitHub Actions: runs tests on every push; runs the morning brief on a schedule.
```

### Layers and their rules

| Layer | File(s) | Rules |
|---|---|---|
| Analytics | `src/pm_agent/analytics.py` | Pure functions. No I/O, no network, no LLM. Every function has known-answer tests. |
| Data | `src/pm_agent/data.py` | Only place that reads files. Raises `ValueError` with a helpful message for unknown portfolio/date/benchmark. |
| MCP server | `src/pm_agent/mcp_server.py` | Calls data + analytics, converts decimals to percent, rounds. No math of its own. |
| Agent | `src/pm_agent/agent.py` | Hand-written loop on the Anthropic SDK + MCP client. No agent frameworks. |
| Morning brief | `src/pm_agent/brief.py` | Uses the same agent with a brief-specific prompt. |
| Evals | `evals/` | Expected answers computed directly from analytics, never typed by hand. |

## 4. Conventions (apply everywhere)

- **Weights are decimals inside the code** (0.05 = 5%). They become percentages only at the
  MCP boundary, in fields ending `_pct` (5.0 = 5%).
- **Money is USD**, fields ending `_usd`.
- **NAV** (net asset value) = sum of position market values + cash.
- **Weight** = position market value / NAV.
- **Short positions** have negative shares, negative market value, negative weight.
- **Long exposure** = sum of positive weights. **Short exposure** = sum of negative weights
  (a negative number). **Gross** = long − short. **Net** = long + short.
- **Active weight** = portfolio weight − benchmark weight (positive = overweight).
- **Trades** are expressed in dollars: positive buys (or covers a short), negative sells (or
  shorts). Cash moves the opposite way.
- Dates are `YYYY-MM-DD` strings. If no date is given, use the latest price date.

## 5. Data

Synthetic sample data lives in `data/sample/` and is generated by
`scripts/make_sample_data.py` (deterministic, seeded). Layout:

```
data/sample/
  portfolios/sample_fund.json   display_name, benchmark, cash, limits, positions [{ticker, shares}]
  benchmarks/sample_large_cap.csv   ticker, weight (sums to 1)
  prices.csv                    date, ticker, close
  securities.csv                ticker, name, sector
```

`PM_AGENT_DATA_DIR` env var overrides the data directory (used by tests and evals).

### The sample fund and its planted story

- ~$50M "Sample Large Cap Fund", ~22 positions across 8 sectors, about 4% cash, one small
  short (INTC, ~2% of NAV) as a hedge.
- Benchmark: a simplified ~23-stock large-cap index (synthetic stand-in for the S&P 500).
  It deliberately excludes a couple of the fund's holdings (AMD, INTC).
- Prices for 5 trading days: 2026-10-16, 10-19, 10-20, 10-21, 10-22. Prices are illustrative,
  not real quotes.
- Shares are set so weights hit their targets exactly on **2026-10-21**.
- **The story the morning brief must find:**
  - Through 2026-10-21, NVDA is ~14.0% of the fund, inside the warning band of its 15%
    single-position limit.
  - On 2026-10-22, NVDA jumps +10% overnight and **breaches** the 15% limit (~15.2%).
  - Also on 10-22: UNH drops −8% (biggest loser), AMD +4%, INTC −3% (the short gains).
  - Selling ~$1M of NVDA resolves the breach without creating new flags. The generator must
    leave clear room here: after the $1M sale, NVDA lands comfortably below the 13.5% warning
    line (90% of 15%), not on the edge of it. A sanity test checks this.
- **Exact flags on each day** (checked by sanity tests, so no other limit trips by accident —
  e.g. benchmark weights are chosen so NVDA's active weight and Tech's sector active weight
  stay inside their limits):
  - 2026-10-21: exactly one flag, the NVDA `max_position` warning.
  - 2026-10-22: the NVDA `max_position` breach, plus only flags we deliberately plant.

### Known simplifications (state these in the README)

- Benchmark weights are static; in reality they drift with prices too.
- Sample data is synthetic. Real data comes in M6.
- No transaction costs, taxes, or settlement in what-if trades.

## 6. Limits

Stored per portfolio in its JSON as decimals:

| Key | Meaning | Sample value |
|---|---|---|
| `max_position` | max absolute weight of any single position | 0.15 |
| `max_stock_active` | max absolute active weight of any stock | 0.05 |
| `max_sector_active` | max absolute active weight of any sector | 0.08 |
| `max_gross` | max gross exposure | 1.15 |
| `min_net` / `max_net` | allowed net exposure range | 0.90 / 1.02 |
| `warn_at` | for max_* rules (except net): warn at ≥ this fraction of the limit | 0.9 |
| `net_warn_buffer` | for net rules: warn within this distance of the limit | 0.02 |

Each flag has `rule`, `subject` (ticker, sector, or "portfolio"), `value`, `limit`,
`status` ("breach" or "warning"). Breaches are listed before warnings. No flags = all clear.
Unknown limit keys raise `ValueError`.

**Flag identity (for comparing before/after a trade):** a flag is identified by
`(rule, subject)`. A breach that becomes a warning on the same `(rule, subject)` counts as a
**resolved breach**, not a new flag. A "new flag" is a `(rule, subject)` that had no flag
before, or a warning that became a breach.

Why net uses a fixed buffer: the net range is narrow (90–102%), so "90% of the limit" would
put any normal value in the warning band.

## 7. MCP tools

All tools are read-only (`readOnlyHint=True`) and return structured output. Default
`portfolio` is `"sample_fund"`. Bad input (unknown ticker, portfolio, date) must return an
error **message the agent can read and act on** (e.g. listing what is available).

| Tool | Inputs | Returns |
|---|---|---|
| `list_portfolios` | – | portfolio names, available price dates |
| `get_portfolio_summary` | portfolio, date | NAV, cash, long/short/gross/net exposure, position counts, benchmark |
| `get_positions` | portfolio, date, top_n (0 = all) | ticker, sector, shares, price, market value, weight |
| `compare_to_benchmark` | portfolio, date, top_n | per stock: portfolio, benchmark, active weight; biggest bets first |
| `get_sector_exposure` | portfolio, date | per sector: long, short, net, gross, benchmark, active |
| `check_limits` | portfolio, date | configured limits, breach/warning counts, flags |
| `simulate_trades` | trades [{ticker, dollars}], portfolio, date | before/after summary + flags, resolved flags, new flags |
| `get_weight_changes` | portfolio, start_date, end_date, top_n | per position: start/end weight, change (pct points), price return |

Tool descriptions matter as much as the code: they are what the model reads to choose a tool.
Each description says what the tool is for and gives an example question it answers.

## 8. The agent

- Hand-written loop: send messages + tool definitions to the Claude API → if the model asks for
  tools, call them through the MCP client → append results → repeat until the model gives a
  final answer or a max-steps limit is hit (default 10).
- Tool definitions come from the MCP server's `list_tools()` at startup (not duplicated by hand).
- System prompt rules:
  1. Every number in an answer must come from a tool result in this conversation. Never estimate.
  2. Use percentages and dollars exactly as tools return them.
  3. If a tool returns an error, read it and fix the call (e.g. use an available date).
  4. Don't give investment advice ("which stock should I buy?"). Explain exposures and the
     effect of trades the user proposes.
  5. Be concise: lead with the answer, then the supporting numbers.
- Model ID comes from the `PM_AGENT_MODEL` env var, not hardcoded in logic. Default:
  `claude-opus-5-5` (Claude Opus 5.5), set in one place.
- Every run is logged: question, each tool call (name, args, duration, error?), tokens in/out,
  total latency, final answer. Logs are what the metrics are built from.

## 9. Morning brief

- `python -m pm_agent.brief --portfolio sample_fund --date 2026-10-22` (date defaults to latest).
- The agent starts broad (`check_limits`, `get_weight_changes`, `get_sector_exposure`), then
  decides what to dig into. It writes a markdown brief:
  - One-line headline (e.g. "1 limit breach: NVDA at 15.2% vs 15% limit").
  - 3–5 ranked items: breaches first, then warnings, then the biggest moves and drifts.
  - Each item: what happened, the numbers, why it matters. If nothing notable, say so plainly.
  - "Calm" means no breaches, not no flags: a quiet day with a warning (e.g. NVDA on 10-21)
    still mentions the warning in one line, without drama.
  - Optional "what you could do" line, **only for breaches**: uses `simulate_trades` to size a
    trade that brings the breach back inside its limit, stated as a fact ("selling ~$1M of
    NVDA would bring it to 13.2%"), never as a recommendation. No suggestions for warnings
    or moves.
- Output saved to `briefs/<portfolio>/<date>.md`. Delivery to Slack/email comes later.
- Scheduling with GitHub Actions: **manual trigger only (`workflow_dispatch`) until real data
  (M6)**, because on sample data the latest date is always 2026-10-22 and a daily cron would
  produce the same brief and spend API credit every day. After M6, add the cron at
  `0 12 * * 1-5` (12:00 UTC weekdays = 7am EST / 8am EDT, before market open either way;
  GitHub cron is always UTC and ignores daylight saving).

## 10. Evals and metrics

### Question-answering eval
- `evals/build_cases.py` generates `evals/cases.json`. Expected values are computed by calling
  analytics directly, so they are always correct.
- 50–100 cases across categories: lookup, calculation, comparison, multi-step, what-if,
  error handling (bad ticker/date), and refusal (investment advice).
- Each case: `id`, `category`, `question`, `expected` (type + value + tolerance),
  `expected_tools`.
- `evals/run.py` runs the agent on every case and records per case: correct?, tools called,
  right tool first?, wasted calls, hallucinated numbers, latency, tokens, cost.
- **Hallucination check:** every number in the final answer must appear (after rounding) in
  some tool result from that run. Numbers that don't are counted as hallucinated.
  Exempt (not counted): numbers that appear in the user's question (e.g. "$1M"), dates, and
  small integers below 10 (list numbering, counts like "3 items").
- Results saved per run (`evals/results/<timestamp>.json` + summary row in a SQLite table)
  so improvements can be charted over time.

### Morning brief eval
- Scenario days with planted events (generated, like the sample data): a limit breach, a big
  move, a quiet day with nothing notable, two events at once.
- Metrics: event recall (did it catch each planted event?), false alarms on quiet days,
  number accuracy (hallucination check), ranking (most important item first).

### Headline metrics for the README
Accuracy, right-tool-first rate, hallucination rate, mean latency, mean cost per question,
brief event recall, brief false-alarm rate — and how they changed across iterations.

## 11. Tech stack

Python 3.11+, MCP Python SDK **v2** (`mcp>=2.3,<3`), Anthropic Python SDK, pandas, numpy,
pytest, SQLite, GitHub Actions, Streamlit (UI + metrics dashboard). Later: yfinance (prices),
SEC EDGAR (13F portfolios, filings), PostgreSQL optional.

## 12. Out of scope (for now)

Agent frameworks (LangChain etc.), real trading or order placement, investment
recommendations, VaR / factor models, intraday data, authentication for the MCP server
(until M8).
